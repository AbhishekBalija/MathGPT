GOAL
====
Build a ChatGPT-style math tutoring platform that:
- Provides teacher-style, step-by-step math solutions
- Verifies each step with SymPy
- UI: Landing page; when logged in -> ChatGPT-style app with Sidebar (chats/history/profile/settings), center Chat Window, right Answer Panel (verified steps)
- Backend: Motia orchestration (JS/TS Steps) + Python Steps for SymPy
- Self-hosted infra (Postgres, Redis, MinIO), Traefik for TLS
- Auth: Google OAuth -> JWT (no Supabase)

PRINCIPLES
==========
- JS/TS: orchestration, API, DB, auth
- Python: SymPy verification only
- Strict JSON contracts between steps
- Harden Python step runtime (no network, non-root, CPU/memory/time limits)
- Frontend built in React + TypeScript + Tailwind
- No arbitrary server-side execution of user code

KEY TECHNOLOGIES
================
- Frontend: React + TypeScript + TailwindCSS, Vite, KaTeX
- Backend: Motia (JS Steps) + Python Steps (SymPy)
- Package Manager: Bun
- DB: Postgres (self-hosted)
- Cache/Rate-limit: Redis
- Object Storage: MinIO (S3-compatible)
- Reverse Proxy/TLS: Traefik (Let's Encrypt)
- CI: GitHub Actions
- Monitoring: Prometheus + Grafana + Sentry
- Frontend Deployment: Vercel

HIGH-LEVEL FLOW
===============
User submits problem in Chat Window (frontend) ->
Frontend POST /api/solve (Motia API step 01-api-solve) ->
01-api-solve validates auth & quota -> calls 02-generate-manifest ->
02 returns JSON manifest -> Motia runs 03-verify-manifest (Python) ->
03 returns verification result -> 04-save-solution persists to Postgres & MinIO ->
Frontend receives completion event or polls -> AnswerPanel displays verified steps.

BACKEND (MOTIA) — DETAILED ROADMAP & FILES
=========================================

BACKEND GOALS
- Steps:
  - 01-api-solve.step.ts (API entry)
  - 02-generate-manifest.step.ts (JS)
  - 03-verify-manifest_step.py (Python SymPy)
  - 04-save-solution.step.ts (JS DB write)
  - 05-export-pdf.step.ts (JS)
  - 06-auth-google.step.ts (API)
  - 07-rate-limit.step.ts (middleware)
- Run Motia Workbench locally during dev
- Harden Python step container
- Postgres for persistence, Redis for rate-limiting, MinIO for PDFs

BACKEND TASK LIST (ordered)
1. Initialize Motia project
   - cd backend
   - bunx create-motia@latest
   - bun install
   - Add scripts: dev, build, start in package.json
   - Commit: "chore(motia): init motia project"
2. Add root requirements.txt
   - Contents: sympy==1.12 pydantic==1.10
   - Commit: "chore(motia): add python requirements"
3. Implement 01-api-solve.step.ts
   - Validate JWT from httpOnly cookie or Authorization header
   - Validate request body via Zod
   - Check rate-limit via calling 07-rate-limit.step.ts (or internal middleware)
   - Call 02-generate-manifest.step.ts (await)
   - Option: return synchronous result (for MVP) or enqueue and return jobId (async)
   - Commit: "feat(backend): add /api/solve entry step"
4. Implement 02-generate-manifest.step.ts
   - Accept: { problem, mode, userId, chatId? }
   - For MVP: produce deterministic manifest (simple JS code)
   - Later: plug in LLM adapter (abstracted with same interface)
   - Emit event `manifest.generated`
   - Commit: "feat(backend): add manifest generator (mock)"
5. Implement 03-verify-manifest_step.py
   - Use Motia Python Step pattern: export config + handler
   - Implement:
     - parse_expr: try latex parser, then sympify fallback
     - check_equiv(a,b): symbolic simplify + numeric fallback
     - derivative_check/integral_check conveniences
     - step timeout and complexity guard (limit expression length, max_ops)
   - Return VerificationResult JSON described earlier
   - Commit: "feat(backend): add sympy verification step"
6. Implement 04-save-solution.step.ts
   - Persist chat/message/solution into Postgres. Use a DB client (pg or prisma)
   - Store JSON steps (jsonb) in solutions table
   - If PDF artifact exists, upload to MinIO and save URL
   - Emit `solutions.saved` event
   - Commit: "feat(backend): persist solution into db"
7. Implement 05-export-pdf.step.ts
   - Use Playwright or chrome-aws-lambda to render HTML to PDF
   - Store result in MinIO and return signed URL
   - Commit: "feat(backend): add export pdf step"
8. Implement 06-auth-google.step.ts
   - Endpoint to accept Google id_token
   - Verify via Google's keys (jwt verify)
   - Create user record if new
   - Issue JWT signed with JWT_SECRET (short expiry + refresh)
   - Commit: "feat(backend): google oauth auth step"
9. Implement 07-rate-limit.step.ts
   - Use Redis token bucket (lua script or sliding window)
   - Hook into 01-api-solve as middleware
   - Commit: "feat(backend): rate-limit step with redis"
10. Cron & backups
    - steps/cron/daily-backups.step.ts: run pg_dump, copy to MinIO
    - Commit: "ops: add daily db backup cron step"

BACKEND DEV NOTES (MOTIA-SPECIFIC)
- Naming: ensure `.step.` or `_step.` is used in filenames to be discovered by Motia.
- Each step should export `config` and `handler` per Motia docs.
- Keep JS steps short; heavy compute in Python steps only.
- Configure Motia step timeouts and resource limits in motia config or via docker options.
- Use Motia Workbench to inspect step input/output locally during dev.

APPENDIX: BASIC API CONTRACTS
============================
POST /api/solve
- Body: { chatId?: string, problem: string, mode: 'step_by_step'|'hint'|'full' }
- Header: Authorization: Bearer <JWT> or httpOnly cookie
- Response (202 queued sync):
  { jobId: string, status: 'queued' }
- Response (sync done):
  { jobId: string, status: 'done', solution: VerificationResult }

GET /api/history
- Returns: [{ chatId, title, lastMessage, updatedAt }]

GET /api/chat/:chatId
- Returns: { chatId, messages[], solution? }

POST /api/auth/google
- Body: { id_token }
- Returns: sets httpOnly JWT cookie; returns { userId, name, email }

VerificationResult
{
  ok: boolean,
  steps: [
    { expr: string, justification: string, status: "VERIFIED"|"CORRECTED"|"FAILED", notes?: string }
  ],
  duration_ms: number
}
